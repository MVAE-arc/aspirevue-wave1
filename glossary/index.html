(01 / 06) Interface Layer

Interface Layer

Where you meet the system.

IDE — Integrated Development Environment

A full-featured editor for writing and running code — file tree, terminal, extensions, and model integrations all in one window.

CLI GUI Antigravity
GUI — Graphical User Interface

Any interface driven by buttons, menus, and windows rather than typed commands. Easier to discover; usually slower to operate than a CLI once you know the verbs.

CLI IDE
CLI — Command-Line Interface

A keyboard-only way to operate a tool — no buttons or menus, just typed commands and their output. Faster than a GUI once you know the verbs; less discoverable until you do.

GUI IDE
Plugin

An add-on that extends a tool’s base functionality without changing the core application. In Obsidian, plugins add features like database views, calendar integrations, and publishing.

(In practice)

The Obsidian vault runs on a curated plugin set. “Core plugin” means it ships with Obsidian by default; “community plugin” means it’s third-party. Core plugins are stable; community plugins vary.

(03 / 06) Model Layer

Model Layer

What’s running underneath.

Tokens

The unit a model uses to measure and process text. Roughly 750 words equals about 1,000 tokens; the model thinks in tokens, not words or characters.

Context Window Usage
Context

Everything the model can currently “see” — the conversation history, any files or documents you’ve loaded, and the system instructions in effect. The model’s responses are shaped entirely by what’s in this context.

(In practice)

When you start a new conversation, context resets. Anything from a prior session that the model needs to know has to be re-loaded — either manually or through a memory system.

Context Window Session Memory Tokens
Context Window

The maximum amount of text a model can hold in a single session, measured in tokens. When it fills up, older content gets compressed or dropped — the model may paraphrase earlier exchanges rather than quote them exactly, and fine detail can drift. In practice, ~70% full is the signal to wrap a session and start fresh to keep output quality consistent.

(In practice)

The Claude Code CLI displays context window percentage during long sessions. When it approaches that threshold, current work gets summarized and a new session picks up from there — no loss of direction, just a clean slate.

Context Session Tokens Prompt Caching
Session

A single uninterrupted conversation with the model. Context builds up within a session and resets when a new one starts. Sessions don’t automatically carry memory forward unless a memory system is configured to do so.

(In practice)

Each working block with the AspireVue OS is effectively a session. The session summary at the end of every block captures what needs to carry forward before context clears.

Context Window Context Memory
Usage

The measured consumption of model capacity — tracked in tokens on API plans, or against a message limit on subscription plans. Different models cost different amounts; more capable models consume more per call.

Tokens API
Prompt Caching

A feature that stores frequently-used context (like a long system prompt or a large reference document) so the model doesn’t re-process it on every call. Reduces cost and latency when the same instructions appear in many requests.

Context Window Tokens API
(04 / 06) Capability Layer

Capability Layer

What the model can do beyond chat.

Agents

A model configured to take sequences of actions — not just answer a question, but plan steps, call tools, read files, and complete a goal with minimal hand-holding between steps.

(In practice)

The morning orientation workflow is an agent: it scrapes email, pulls the calendar, surfaces project status, and assembles a brief — all in one run, triggered by a single button press.

Sub-Agents Agent Teams Tools / Tool Use Skills Hooks
Sub-Agents

An agent spawned by another agent to handle a focused part of a larger task. The parent agent delegates and reassembles; the sub-agent executes and returns. Different from Agent Teams, which is a persistent multi-role infrastructure — sub-agents are disposable task-runners within a single run.

Agents Agent Teams
Agent Teams

A persistent multi-agent setup where specialists share a task list and pick up work as it comes in. The team holds context across runs; each agent has a defined role. Different from spinning up a sub-agent for one task — the team is always there, ready to claim work.

(In practice)

As the AspireVue OS matures, standing agent teams handle recurring work categories — clinical summaries, BD conversations, ideation scoring — without needing to be rebuilt each time.

Agents Sub-Agents Skills Hooks
Skills

Packaged sets of instructions that an agent loads before starting a specific type of task. A skill tells the agent how to approach a category of work — what rules apply, what format to use, what to avoid. Think of it as a standing brief, not a prompt you type each time.

(In practice)

A skill called before drafting client-facing copy might specify register, banned phrases, structural variety, and accuracy rules — so the agent loads a consistent standard rather than improvising every time. The same pattern applies to research, intake, summarization, or any recurring work category.

Agents System Instructions Slash Commands
Memory

A mechanism for persisting information across sessions. Without memory, every new conversation starts blank. With it, the agent recalls prior decisions, user preferences, and project context without being re-briefed each time.

(In practice)

The AspireVue OS uses a file-based memory system inside Obsidian. Session summaries and decision logs write to that memory so the next session picks up with full context rather than starting cold.

Context Session Vault Obsidian
Tools / Tool Use

The ability to call external functions during a conversation — read a file, run a search, send a request to an API, write to a calendar. The model decides when a tool is needed and calls it mid-response.

Agents MCP API Hooks
Slash Commands

Typed shortcuts that trigger predefined behaviors — e.g., “/compact” to compress session history when the context window gets tight, or “/clear” to reset. Available in Claude Code CLI; the specific commands depend on what’s configured.

CLI Context Window Skills
Hooks

Automated triggers that fire at defined points in an agent’s lifecycle — before a task starts, after it completes, when a tool is called. Used to enforce consistent behavior (like always loading a skill before certain types of output) without relying on the agent to remember.

(05 / 06) Integration Layer

Integration Layer

How the system reaches outside itself.

API — Application Programming Interface

A defined channel for one piece of software to talk to another — structured requests in, structured responses out. When Claude connects to Gmail or Google Calendar, it’s going through those services’ APIs.

MCP Tools / Tool Use
MCP — Model Context Protocol

An open standard for connecting AI models to external tools, data sources, and services in a consistent way. Instead of building a one-off integration for every tool, MCP provides a common interface — the model speaks MCP, and any MCP-compatible server can respond. Gmail, Google Calendar, Obsidian, and others have MCP servers.

(In practice)

MCP connections are how the morning orientation workflow reaches into Gmail and Google Calendar. Larry’s Outlook/Gmail question from Session 1 is an MCP scoping question — which server to configure depends on which service holds the live calendar.

API Tools / Tool Use Agents
System Instructions

A set of operating principles loaded into an agent at the start of every session, governing how it behaves across all of its work — tone, format, constraints, priorities. Also called “system prompt” or “custom instructions” depending on the interface. These can be tiered: global instructions that apply everywhere, and task-specific instructions that apply only to certain types of work.

(In practice)

Larry’s custom template in the Claude app is a system instruction — it tells the model how to handle every “AspireVue meeting” recording before it reads a single word of the transcript.

(06 / 06) Vault Layer

Vault Layer

Where your knowledge lives.

Vault

The folder that Obsidian treats as your knowledge base — all notes, templates, attachments, and configurations live inside it. Obsidian reads the vault as a unified graph, not just a pile of files.

(In practice)

The AspireVue OS vault holds session summaries, agent memory, project notes, trigger-word logs, and workflow templates. Nothing important lives only in a chat window; it gets written to the vault so it persists.

Obsidian Wiki-link Canvas NOW doc Plugin
Wiki-link

The “[[Note Name]]” syntax that creates a clickable, bidirectional connection between two notes. Click it to navigate; the linked note also shows all notes that point to it. This is the connective tissue that makes a vault navigable as a knowledge graph rather than just a folder of files.

(In practice)

Session summaries are wiki-linked to the relevant project note, the promise ledger, and the NOW doc. That’s what makes a summary findable from three different entry points without duplicating it.

Vault Obsidian Canvas
Canvas

Obsidian’s native node-and-edge visual surface for mapping architecture, workflows, and relationships. You place notes, text blocks, and images as nodes; draw edges between them to show connections. Each canvas is a .canvas file in the vault.

(In practice)

The Plaud workflow overview you received after Session 1 was built as a Canvas — nodes for each step in the flow, edges showing the routing logic. It’s a live document, not a screenshot.

Vault Obsidian Wiki-link
NOW doc

A single always-live document inside the vault that surfaces what is active right now — top priorities, hot threads, next moves. Not a to-do list; more like a cockpit readout. The exact update cadence is something each operator tunes — some refresh it at the end of a working block, some at the start of the next one, some both.

(In practice)

In the AspireVue OS, the NOW doc is the daily anchor — open it first, work from there. When the system is running well, you don’t have to remember where you left off; it’s already named.
